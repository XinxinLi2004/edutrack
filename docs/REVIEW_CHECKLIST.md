# Eduflow 人工审查清单（8 维度）

> 用途：① 作者提交前**自审**；② Reviewer **人工审查**时逐条过。
> 用法：每条打 ✅（通过）/ ❌（问题）/ ➖（不适用）。标 🔴 的为阻塞项，必须修完才能合并。

---

## 1. 代码风格（机器大多已挡，这里查漏）
- [ ] 是否已跑 `pre-commit` / CI 格式化检查通过
- [ ] 命名是否见名知意（无 `a`/`tmp`/`data2` 之类）
- [ ] 无被注释掉的死代码、无“留着以后用”的废代码 🔴

## 2. 可读性
- [ ] 单函数 ≤ 50 行，超过已拆分
- [ ] 嵌套 ≤ 3 层，过深处已抽函数
- [ ] 无重复 3 次以上的相同逻辑（已抽公共函数）
- [ ] 无裸魔法值（已提为具名常量/配置）
- [ ] 复杂逻辑有“为什么”的注释，无废话注释
- [ ] 写法直白，半年后的自己能一眼看懂

## 3. 文档与规范
- [ ] 新公共函数/类有 docstring（参数/返回/异常）
- [ ] 新模块有职责说明（README 或包 docstring）
- [ ] 接口变更已在 PR 模板填了方法/路径/入参/出参/错误码
- [ ] PR 描述让人能看懂“做了啥/为啥/怎么测”
- [ ] 新人能照 README 跑起项目

## 4. Bug 防护 🔴
- [ ] 对 None / 空列表 / 空字符串 / 0 显式处理
- [ ] 异常捕获具体（`except ValueError:`），无裸 `except:`，不吞错
- [ ] 文件/连接/游标用了 `with` 或 `try-finally` 释放
- [ ] 无跨请求的可变全局状态泄漏
- [ ] 函数尽量有类型注解，未用 `Any` 掩盖问题
- [ ] 关键分支/错误有日志，且未打印敏感信息

## 5. 安全性 🔴
- [ ] SQL 全部参数化 / ORM，无字符串拼接
- [ ] 无硬编码密钥/密码（用环境变量/密钥管理），`.env` 未提交
- [ ] 受保护接口已鉴权；未信任前端传的 userId（防越权）
- [ ] 所有外部输入（请求体/参数/上传文件）已校验清洗
- [ ] 第三方依赖无已知高危 CVE（pip-audit / npm audit）
- [ ] 前端无 `v-html` 渲染未净化内容；关键操作有 CSRF 防护

## 6. 结构
- [ ] 分层清晰（路由/服务/数据访问不跨层调用）
- [ ] 单一职责：无上帝类 / 万能函数
- [ ] 模块依赖明确、低耦合、无循环依赖
- [ ] 环境相关值（端口/密钥/开关）已配置外置，无写死
- [ ] 新文件放到了正确的目录位置

## 7. 可持续性
- [ ] 核心逻辑/工具函数有单测；改 Bug 先补复现测试
- [ ] 关键路径有日志/埋点，出错可追踪
- [ ] 接口变更向后兼容，或已显式版本化
- [ ] 临时方案加了 `TODO(owner): 原因+计划`，非无期限
- [ ] 无循环内查库 / N+1 查询 / 全表扫描等明显性能问题

## 8. 架构（仅重大改动/定期评审时关注）
- [ ] 符合既定分层架构，未引入不当耦合
- [ ] 新需求能低成本接入，无需四处改
- [ ] 引入新框架/库已评审，无重复造轮子/过度设计
- [ ] 数据模型/接口契约合理，演变可控

---

## 审查结论模板

```
审查结论：✅ 通过 / 🟡 需修改 / 🔴 阻塞
阻塞项（必须修）：
1. ...
建议项（建议修）：
1. ...
其他：
-
```

> 小团队提示：作者提 PR 后**自己先按此清单再审一遍 diff**（隔半天/第二天效果更好），
> 关键或高风险改动再请对方互审。这样能把 80% 的问题在合并前消掉。
